# 01. 작업 방식 — 서리마을을 어떻게 만들었나

> **대표님용 요약**
> - 대표님이 레퍼런스(화이트아웃 서바이벌 광고)와 아이디어를 주면, Claude가 **기획서 → 기술 계약서 → 여러 팀 동시 제작 → 하나로 합치기 → 여러 관점 검수 → 수정 → 다시 확인 → 플레이 링크** 순서로 만들었어요.
> - "팀"은 Claude가 띄운 여러 AI 작업자(에이전트)예요. 캐릭터 팀, 건물 팀, 사운드 팀, 이펙트 팀, 코드 팀이 **동시에** 일했어요.
> - 동시에 일해도 안 엉키게 한 비결은 **계약서**(모든 그림의 각도·크기·이름 규칙)를 먼저 정한 거예요.
> - 모든 작업은 클라우드 컴퓨터에서 했고, 대표님 PC는 쓰지 않았어요.

## 1. 전체 흐름 (실제 순서와 걸린 시간)

| 단계 | 한 일 | 결과물 | 대략 시간 |
|---|---|---|---|
| 0. 레퍼런스 분석 | 광고 이미지에서 장르·시점·핵심 재미 뽑기 (아이소 시점, 탑 쌓기, 손님 줄) | — | 몇 분 |
| 1. 환경 확인 | 컨테이너에서 쓸 수 있는 도구 확인: `pip install bpy` 로 Blender 5.2 설치 성공, Cycles만 동작, 허깅페이스 차단 확인 | 도구 목록 | 10분 |
| 2. 기획서 | 한국어 기획서 (코어 루프, 직업 5개, 생산 라인, 해금 순서, 아트/사운드 방향) | `docs/기획서.md` | 10분 |
| 3. 기술 계약서 | 투영(카메라 각도), PPU 64, 앵커, 매니페스트 형식, **모든 에셋 키 이름**, 코드 규칙 | `docs/CONTRACT.md` | 20분 |
| 4. 공용 기반 | `bl_common.py`(카메라·조명·재질), `pack_utils.py`(아틀라스 패킹) 를 직접 작성하고 **테스트 렌더로 각도·앵커 검증** | 공용 도구 | 20분 |
| 5. 병렬 제작 | 5팀 동시: 캐릭터(Blender), 소품·건물(Blender), 사운드(합성), 이펙트·UI·바닥(그림 생성), 게임 코드(Phaser). 코드는 에셋이 없어도 대체 그림으로 돌아가게 | 에셋 폴더 + 매니페스트 + 게임 | 각 50~100분 |
| 6. 통합 | 실제 에셋을 게임에 연결, 헤드리스 크롬으로 처음부터 끝까지 자동 플레이, 스크린샷 확인 | 플레이 가능한 게임 | 코드 팀이 겸함 |
| 7. 다관점 검수 | 4명 동시: 게임플레이 봇(실제 입력으로 플레이·시간 측정), 화면, 안정성·성능, 배포 | 발견 사항 56개 (치명 2) | 1~2시간 |
| 8. 수정 → 독립 검증 | 수정 담당이 **먼저 재현**하고 고침 → 다른 검증 담당이 다시 확인 + 최종 스크린샷 | 고친 게임 | 2~3시간 |
| 9. 확장 | 주민 17명+동물 3, 이모티콘, 생활 소품 — **계약서 부록 + 새 폴더**로 충돌 없이 | `CONTRACT_VILLAGERS.md` | 약 100분 |
| 10. 배포 | 아티팩트(플레이 링크)용 번들 → 실제 호스팅 환경 흉내 테스트 → 공개 | 테스트 링크 | 20분 |

## 2. 팀(에이전트) 운영 방법

### 2-1. 계약서가 핵심
- 그림을 그리는 팀과 코드를 짜는 팀이 서로 기다리지 않으려면, **이름과 규칙을 먼저 못 박아야** 해요.
- 계약서에 정한 것: 카메라 각도(고도 30°, 방위 45°), 크기(1m = 64픽셀), 발 위치(앵커), 방향 이름(S, SE, E, NE, N), 프레임 이름(`walk_SE_3`), 매니페스트 형식, 에셋 키 전체 목록(`item_fish_cooked`, `station_grill` …), 게임 코드 규칙(경고창 금지, 저장소 접근은 try/catch, 테스트 훅).
- 확장할 때는 계약서를 고치지 않고 **부록**(`CONTRACT_VILLAGERS.md`)과 **새 폴더**(`assets/villagers/` 등)를 만들어서, 이미 돌아가는 것과 안 부딪히게 했어요.

### 2-2. 팀마다 "내 폴더"를 정해줌
| 팀 | 쓸 수 있는 곳 |
|---|---|
| 캐릭터 | `tools/blender/char_*.py`, `assets/characters/`, `docs/previews/char_*` |
| 소품·건물 | `tools/blender/prop_*.py`, `assets/props/` |
| 사운드 | `tools/audio/`, `assets/audio/` |
| 이펙트·UI·바닥 | `tools/fx/`, `assets/fx/`, `assets/ui/`, `assets/ground/` |
| 게임 코드 | `index.html`, `src/`, `tools/test/` |
| 주민 (확장) | `tools/blender/vil_*.py`, `assets/villagers/` |
| 생활 소품 (확장) | `tools/blender/life_*.py`, `assets/life_props/` |
| 이모티콘 (확장) | `tools/fx/gen_emotes.py`, `assets/emotes/` |

- 공용 파일(`bl_common.py`, `pack_utils.py`)은 아무도 못 고치게 하고, 필요하면 자기 파일에서 감싸서 쓰게 했어요.
- git 커밋은 리더(메인 Claude)만 해요.

### 2-3. 각 팀에게 준 지시의 공통 뼈대
1. 먼저 읽을 것: 계약서, 기획서, 레퍼런스 이미지, 이미 만든 미리보기
2. 소유 폴더와 금지 사항
3. 도구와 제한 (Bash 10분 제한 → 긴 작업은 이어하기 가능하게 / 백그라운드)
4. 품질 기준: **자기 결과물을 이미지로 직접 보고** 레퍼런스와 비교하며 반복 수정
5. 먼저 한두 개로 룩뎁(look-dev: 스타일 잡기) → 다듬기 → 나머지 대량 생산
6. 검사 스크립트로 빠진 것 0개 확인
7. 최종 보고: 경로, 키, 계약서와 다른 점, 다음 팀에게 줄 메모 (구조화된 형식)

### 2-4. 검수 → 수정 → 검증
- 검수는 서로 다른 관점의 4명이 **읽기 전용**으로: ① 게임플레이(봇이 실제 조작으로 플레이하며 시간 측정, 막히는 곳 찾기) ② 화면(여러 기기 크기 스크린샷) ③ 안정성·성능(저장 깨짐, 10분 이상 장시간, 메모리, 사운드) ④ 배포(GitHub Pages, 플레이 링크 환경 흉내).
- 수정 담당은 모든 발견 사항을 받아 **재현 → 수정 → 자동 테스트 통과**까지.
- 마지막 검증 담당이 의심하는 눈으로 다시 확인하고 최종 스크린샷을 찍어요.
- 실제로 찾은 치명 버그: 광부 고용 발판이 입구 안에 있어 밟을 수 없음(게임 완료 불가), 산 손님이 사라지지 않아 계속 쌓임.

### 2-5. 사용자와 소통
- 큰 단계마다 미리보기 이미지를 보여주고, 진행 상황을 한국어로 짧게 알림.
- 중간에 **테스트 플레이 링크**를 만들어 바로 해볼 수 있게 함 (사용자가 "테스트 버전 없어?"라고 물어봄 → 기다리게 하지 말고 그때그때 링크 제공).
- 큰 방향은 추천안과 함께 질문 (예: 쉬운 휴대폰 방식 vs 세틀러식 직접 건설).

## 3. 새 프로젝트에서 이 방식 그대로 쓰기
1. 대표님과 기획 초안(`07_세틀러식_새게임_기획초안.md`)을 정한다.
2. 새 게임용 **계약서**를 쓴다 — 전작 `CONTRACT.md` 를 바탕으로 PPU·카메라는 그대로 두고(기존 그림 재사용), 새로 필요한 키(길·깃발·건설 단계·영토 등)를 추가.
3. `reference/frost-village/tools` 를 새 게임 폴더로 복사, 재사용할 에셋 복사.
4. 프로토타입(작은 지도 + 건물 3~4개 + 길 + 짐꾼)을 먼저 만들어 재미를 확인하고, 그다음 팀을 나눠 확장.
5. 매 단계 끝에 검수 → 수정 → 검증, 그리고 플레이 링크.
